MAJOR — `dashboard/template.html` renderDescribe → "Stars' answer vs the model's answer, per class" (all tabs; worst on `first100_v3`); ISSUES Step 7 "Descriptive layer design" — The paired bars compare only row totals with column totals, so errors that cancel out are hidden. A class the model never got right can look perfect. ISSUES says this chart makes "Over- and under-prediction ... visible without drilling in", and the card is where Step 7 says failures should be "visible at a glance". On the lopsided three-class run it shows the opposite of what happened. — Evidence: on the `first100_v3` tab (`page_dump.txt` lines 417–420) the chart reads "Neutral / Stars 2 / Model 2", two bars of identical length (3.3px each, `scale_check.txt`). In `runs/first100_v3/metrics.json`, `per_class.NEUTRAL.correct = 0`, `confusion_cells["NEUTRAL->POSITIVE"] = 1`, `["NEUTRAL->NEGATIVE"] = 1`, `["POSITIVE->NEUTRAL"] = 2`. All 4 reviews involved are errors, yet the bars match. On `balanced150_v3`, "Positive / Stars 50 / Model 57" suggests 7 extra POSITIVE answers. The real count is 11 errors touching POSITIVE: 9 false positives (8 from 3★, 1 from 1–2★) plus 2 misses, and 48 right. The binary tabs show "Positive 93 / 92", which hides 3 errors. — Suggested fix: split each Model bar into right (slate) and wrong-from-other-classes (amber), or add a third "Model, right" bar from `per_class.<k>.correct`. At minimum, say in the sub-caption that equal totals do not mean correct answers. Soften the ISSUES claim to "net over/under-prediction".

MAJOR — `dashboard/template.html` renderDescribe `starChart` (`.hbar` = `.htrack` flex:1 + count + share), all tabs, both viewports; template comment "on one 0-100% scale, so the whole file and a sample of 100-150 compare directly"; ISSUES "on the same 0–100% share scale" — The two star charts are drawn at different scales, and rows within the whole-file chart are too. Each row is its own flex line, so a wider count label ("128,248" vs "50") takes width from that row's track. This is the "label/positioning interaction" the assignment warns about, just not severe enough to collapse a bar. `verify_dashboard.py` only checks ≥2px and a printed label, so it cannot catch it. — Evidence (`scale_check.txt`, 1440px):
  - Whole file 5★: 84.1%, bar 152.6px, track 181.3px, 1.81 px per 1%.
  - Whole file 4★: 4.4%, bar 8.6px, track 197.0px, 1.96 px per 1%.
  - Sample (every run and row): track 216.3px, 2.16 px per 1%.
  - So batch_100's 5★ at 91.0% draws at 196.8px against the file's 84.1% at 152.6px: 29% longer for 8% more share. This visually overstates the "batch_100 exaggerates the skew" point made in ISSUES.
  - At 400px it is the same (1.84 vs 2.19 px per 1%).
  - Suggested fix: give the star-chart grid fixed columns (name | track | count | share) shared by both charts, e.g. one grid with `grid-template-columns: 30px minmax(0,1fr) 7ch 6ch` and equal-width blocks, so the track width is the same for every row in both charts. Add a check in `verify_dashboard.py` that bars claiming a shared scale have equal px-per-unit, within 1% or 1px.
