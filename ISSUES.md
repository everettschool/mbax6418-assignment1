## Step 0 — Environment

- **[Step 0] `pdftotext` not installed** — poppler is absent on this Mac. Extracted `docs/assignment.pdf` with `pypdf` inside the project virtualenv instead (allowed by the build prompt).
- **[Step 0] System Python is 3.9** — `/usr/bin/python3` is 3.9.6. Built the virtualenv (`.venv/`) with Homebrew Python 3.14.2 for current `openai`/`playwright` wheels.
- **[Step 0] `prompt.md` git-ignored** — the agent orchestration prompt sits in the project root and mentions the endpoint host by name. It is not a deliverable, so it is excluded via `.gitignore` to keep the host name out of the tracked tree.
- **[Step 0] Metadata kept in predictions files** — decision: carry `verified_purchase`, `helpful_vote`, `timestamp`, `asin`, `parent_asin`, and `images_count` (length of `images`) into every `predictions.jsonl` row, for slicing errors later (e.g., are unverified reviews harder?). Dropped `user_id` (a reviewer identifier with no analytic use here, and no reason to republish it) and the raw `images` URLs (bulky). None of these fields is ever passed to the model; `build_messages` accepts only `title` and `text`.
- **[Step 0] Inclusion rule** *(addition)* — rows whose `text` is empty after stripping whitespace are excluded from every run. 49 of 152,410 rows fail it (by rating: 1★ 18, 2★ 3, 3★ 1, 4★ 1, 5★ 26). The assignment says "first 100 rows"; `batch_100` is defined as the first 100 `review_id`s that pass the rule. In practice none of rows 0–99 fail it, so `batch_100` is exactly review_ids 0–99 (see Step 2).
- **[Step 0] Model is a "thinking" model; first call returned no answer** — `cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit` (the only model `/v1/models` offers) spent all 200 `max_tokens` on a hidden `reasoning` field and returned `content: null`, `finish_reason: length`. Passing `extra_body={"chat_template_kwargs": {"enable_thinking": false}}` (a vLLM chat-template switch) made it answer `LABEL=POSITIVE` directly with 0 reasoning tokens in 0.5 s. Decision: every classification call disables thinking, so `max_tokens` can stay small as the parse policy requires; the setting is recorded in each `run_meta.json`. `temperature=0` was accepted without error.
- **[Step 0] Imbalance confirmed at the source** — full file: 5★ 84.1%, 4★ 4.4%, 3★ 2.1%, 2★ 1.2%, 1★ 8.1% (`runs/rating_distribution.json`). Binary truth (≥4 positive) is therefore ~88.5% POSITIVE across the file, so a model that always says POSITIVE scores ~88% before doing anything useful.

## Step 1 — Structured prompt, binary

- **[Step 1] Indirect rating leak through auto-generated titles** — while reading spot-check candidates, titles such as "Five Stars", "Three Stars", "One Star" turned up. Counting over the 152,361 included rows: 31,868 titles (20.9%) are exactly "<One–Five> Star(s)" (1★ 684, 2★ 139, 3★ 428, 4★ 1,653, 5★ 28,964), and the number equals the rating in 31,838 of them. They are Amazon's auto-filled titles, i.e. the rating itself. Passing them would break "the model never sees the rating". Fix: `build_messages` blanks a title (or a text — 13 texts are only such a phrase) that fully matches `^(one|two|three|four|five) stars?$`; the prompt says either field may be empty. The stored `title`/`text` in predictions stay original; `verify_leak.py` rebuilds the messages and asserts no such phrase was sent. Done before any run used `sentiment_v1.txt`, so the prompt was still editable.
- **[Step 1] Residual path, not closed: customers who mention stars in their own words** — 909 included texts say things like "5 stars" or "one star because…" inside longer text. That is the customer's review content, which the assignment tells us to classify, so it is left intact and disclosed rather than rewritten. `verify_leak.py` counts these per run.
- **[Step 1] Parser self-test caught a code-fence bug** — the first fence-stripping regex (`^`+[a-zA-Z]*`) treated `LABEL` in a single-backtick reply `` `LABEL=POSITIVE` `` as a fence language tag and deleted it, so a valid answer would have been counted FAIL. Fixed: a line that is only a fence (```` ``` ```` / ```` ```text ````) is skipped; other lines have backticks trimmed from both ends. `src/test_classify.py` covers both forms.
- **[Step 1] `openai` 3.x uses `httpx2`** — the self-test's `import httpx` failed; the SDK now depends on `httpx2`. Switched the import.
- **[Step 1] `verify_leak.py` crashed on a relative extra-file path** — `Path.relative_to` needs absolute paths; it also left a temp file in `reviews/`. Now resolves the path and writes the temp file under git-ignored `cache/`; the stray file was deleted.
- **[Step 1] Spot check 10/10** — 5 clearly positive and 5 clearly negative reviews picked by reading only (review_ids 1043, 1113, 1197, 1218, 1232 / 1453, 1624, 2473, 3637, 4511, all outside `batch_100`); the model's labels matched reading on all 10, and the ratings revealed afterward (five 5★, five 1★) agreed too. Caveat: picked for being obvious, so this proves the plumbing, not accuracy. Evidence: `reviews/step1_spotcheck.txt`, `.json`.

## Step 3 — Dashboard

- **[Step 3] Charts built from HTML/CSS marks, not SVG** — the build prompt prefers inline SVG. I used flex/grid `div` marks instead: text labels never get stretched by an SVG `viewBox`, the layout reflows on narrow screens, and every fill is still a CSS custom property from the single `:root` block, so recoloring works the same. Every mark carries `data-run`, `data-metric`, `data-value`, and `data-label`, and has `min-width/min-height: 2px` so a non-zero value cannot collapse.
- **[Step 3] Palette chosen by running the dataviz validator, not by eye** — class identity uses blue `#2f5aa8` (POSITIVE), vermilion `#c8502e` (NEGATIVE), and violet `#6e56b8` (UNPARSED): all checks pass, worst adjacent CVD ΔE 20.6. NEUTRAL is a deliberate warm gray `#8f8a7e` (fails only the chroma floor, by design, as a neutral midpoint; always shown with a text label). The first right/wrong pairs, green vs pink (`#237a57`/`#c23a6b` and two variants), **failed** colorblind separation (deutan ΔE 2.8–5.4). Switched to slate `#3e4a57` for right vs amber `#d9822b` for wrong (CVD ΔE 26.7): mistakes are the loud color and correct answers recede. Amber is under 3:1 contrast against the surface, so every amber mark also carries a visible count.
- **[Step 3] Nested children rendered as "[object HTMLSpanElement]"** — the first headless screenshot showed the precision footnote printing object names: the DOM helper flattened children one level only. Fixed with `flat(Infinity)`; caught by looking at the screenshot, not by any assertion, which motivates the text checks in `verify_dashboard.py` (Step 4).
- **[Step 3] Raw review text contains HTML** — the dataset text includes `<br />` and entities such as `&#34;`. The model received the text exactly as stored. For display only, the page renders them as line breaks and characters (still inserted as text, never as HTML). The saved predictions are unchanged.
- **[Step 3] Build guard against network URLs** — `build_dashboard.py` refuses a template containing `http://` or `https://`, so the page cannot fetch anything. Headless load of the built page recorded 0 non-file requests and 0 console errors.
- **[Step 3] Numbers Auditor round 1: 0 mismatches, 2 MINOR, both fixed** — `reviews/step3_numbers_auditor.md` compared 62 metric fields, 56 tagged numbers and 14 chart marks in headless Chromium against its own recomputation: all equal. (1) The table's "of 100 reviews" total was computed in the page (`rows.length`) with no `data-source`; it is now `metrics.json#n_rows` with full data attributes, and the shown count carries `data-live-count` for Step 4's filter checks. (2) The run blurb in `manifest.json` repeated run facts by hand ("first 100", the star rule); the blurb is now built from `run_meta.json` fields (`n_rows`, `selection_rule`, `prompt_file`, `label_scheme`) as tagged spans, and `build_dashboard.py` refuses to build if a tab label's number differs from `n_rows` or its class wording differs from `label_scheme`. None rejected.

## Step 4 — Interactive filtering

- **[Step 4] Filter design** — four combinable filters above the review table: Result (all / matches / mistakes), Answer key class, Model's predicted class (including Unparsed), and free-text search, plus Reset and a live "Showing N of M reviews" count. Search is case-insensitive substring over title + text, matching either the stored text or its display form (so `4"` finds a review stored as `4&#34;`). Filters reset when switching runs.
- **[Step 4] Confusion cells filter the table** *(addition)* — clicking (or Enter on) any non-zero heatmap cell sets the Answer key and Model filters to that cell and scrolls to the table, so each error count in the matrix leads straight to the reviews behind it.
- **[Step 4] `src/verify_dashboard.py`** *(addition — the assignment asks to check page numbers "in the browser", this makes it mechanical)* — in headless Chromium it (A) resolves every `data-source` and compares file value, `data-raw`, and displayed text under the display rule (mirroring JavaScript `toFixed` rounding exactly with `Decimal` ROUND_HALF_UP on the binary value, not Python's half-even `format`); (B) checks every chart mark's value against its saved field and that non-zero marks render ≥ 2px in both dimensions; (C) for each filter and combination, compares the *set* of visible review_ids (not just the count) with the rows computed from `predictions.jsonl`, and the count text and `data-live-count`; (D) fails on console errors, network requests, > 1 MB, or any untagged percentage outside the table.
- **[Step 4] Verifier passes, and was shown to fail when it should** — on the built page: 294 checks, 0 failures (60 metric numbers, 14 marks, 17 filter cases; `reviews/step4_verify_dashboard.txt`). A verifier that only ever passes proves little, so three deliberately broken copies of the page (kept in git-ignored `cache/mutations/`) were run through it: a wrong embedded accuracy (0.97→0.96) → exit 1, 4 failures; inverted match/mistake filter logic → exit 1, 15 failures; chart marks forced to 0px → exit 1, 8 failures ("value 93 renders at 0.00x16.00px"). All three caught (`reviews/step4_verify_mutation.txt`). Clicking the Positive→Negative heatmap cell set both filters and showed "Showing 2 of 100 reviews", matching `metrics.json` `confusion_cells` = 2.
- **[Step 4] Tooltip stayed on screen after a heatmap click** — seen in the filtered-state screenshot: the cell's tooltip ("2 · Stars: Positive → model: Negative") remained over the review table after the click scrolled the page, because tooltips only hid on pointer movement or focus loss. Fixed in Step 5 by hiding the tooltip on any click or scroll.

## Step 5 — Primary emotion, two ways

- **[Step 5] Prompt v2 is a new file; v1 untouched** — `prompts/sentiment_v2.txt` keeps every v1 sentiment rule verbatim and adds task two: one primary emotion from exactly anger, anticipation, disgust, fear, joy, sadness, surprise, trust, in lowercase, each with a one-line gift-card-context gloss. Policies chosen: judge the *reviewer's* emotion, not the recipient's (unless the reviewer shares it); a flat, matter-of-fact review still gets the closest of the eight, because the assignment asks for one primary emotion and has no "none" option. Output line: `LABEL=<X>;EMOTION=<Y>`. Like v1, the prompt contains no digits and none of rating/star/stars/helpful/verified.
- **[Step 5] Adding the emotion task did not change sentiment on batch_100** — `first100_v2` has 0 rows whose sentiment prediction differs from `first100_v1`; the same three reviews are wrong (17 and 46 POSITIVE→NEGATIVE, 98 NEGATIVE→POSITIVE), 0 parse failures, 0 retries, 90 API calls + 10 cache hits. `verify_leak.py` passes for both runs (`reviews/step5_verify_leak.txt`).
- **[Step 5] LLM emotions are concentrated in one label** — on batch_100 the model answered joy 80, trust 9, anger 7, anticipation 3, disgust 1 (fear, sadness, surprise 0). With 93 positive reviews this is expected, but it means emotion agreement on this batch will mostly measure whether the word list also says joy.
- **[Step 5] Official NRC download refused Python's default client (HTTP 406)** — `curl -I` on the official zip returned 200, but `urllib` with its default `Python-urllib` User-Agent got `HTTP Error 406: Not Acceptable`, and the NRCLex fallback was not installed, so the first `get_nrc.py` run crashed. Fix: the request now carries a User-Agent that honestly names this script (`mbax6418-assignment1-get_nrc/1.0 (python urllib)`), with a `curl` retry of the same official URL if it is still refused and NRCLex only as a last resort. The second run succeeded on the first client: `download_client: urllib`, official source used, no fallback needed.
- **[Step 5] Lexicon recorded, not committed** — NRC Emotion Lexicon v0.92 word-level file (`NRC-Emotion-Lexicon/NRC-Emotion-Lexicon-Wordlevel-v0.92.txt` inside the official zip). zip sha256 `4edcbd00…34e6`, word file sha256 `02c66154…535a`, 14,154 words, 4,454 with at least one of the 8 emotions; full values in `runs/nrc_lexicon_meta.json`. The zip and word file live in git-ignored `data/nrc/`; `nrc_emotion.py` refuses to run if the file's hash differs from the recorded one.
- **[Step 5] Lexicon license shapes what is committed** — the lexicon's bundled README (section IX, Terms of Use) allows free non-commercial research and educational use, requires citing Mohammad & Turney (2013), and forbids redistribution. So the lexicon files stay out of the repo, the README will cite the papers and link the lexicon home page, and a reader re-downloads it with `src/get_nrc.py`. Decision: each prediction row keeps `nrc_hits` (the review's own tokens, the lexicon word they matched, and that word's emotions), because the Step 5 comparison must be grounded in each review's lexicon hits and auditable. That is a small per-review excerpt tied to review text, not a copy of the lexicon; the full word list is never written to a tracked file.
- **[Step 5] Emotion agreement is no better than a constant "joy" answer** — LLM vs word list: 20/100 (20.0%) all rows, 20/85 (23.5%) excluding NONE, 20/38 (52.6%) excluding NONE and TIE. A constant answer of "joy" (the LLM's most common emotion) scores 22/100, 22/85, 22/38 against the same word list, so the LLM is 2.0 points below it overall and 5.3 points below where the word list has one winner; where the LLM did not say joy, the two agree on 1 of 20 reviews. The word list tied on 47 rows (9 of them in the duplicate "Good Product" groups; removing the 7 repeats leaves 40 ties among 93 unique reviews) and found nothing on 15. Written up in `reviews/step5_analysis.md`.
