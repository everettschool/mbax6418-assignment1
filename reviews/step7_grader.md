Findings:

MAJOR — `dashboard/template.html` `renderDescribe` → `starChart` (lines 444–454), plus the ISSUES.md Step 7 "Descriptive layer design" entry — The two star-distribution charts claim to share "one 0–100% scale" (template comment) and to be "on the same 0–100% share scale" (ISSUES.md), so the whole file and the sample can be compared by bar length. In pixels this is false. Each bar's width is a percentage of a flex track, and the track is whatever space the count label leaves in that row. So the scale changes from row to row within the file chart, and again between the two charts. This is the label/positioning interaction Step 7 warns about: here it distorts bars rather than collapsing them, and `verify_dashboard.py` only checks bars ≥ 2px, so it does not catch it — evidence: `.venv/bin/python reviews/step7_grader/measure.py` (1440px, balanced150_v3):
  `rating_counts.5 v=128248 w=152.58 track=181.3` · `rating_counts.4 v=6692 w=8.64 track=197.0` · `rating_counts.1 v=12326 w=15.30 track=189.2` · `sample_rating_counts.5 v=50 w=72.08 track=216.3`; summary line `track widths per chart: {'rating_counts': [181.3, 189.2, 197], 'sample_rating_counts': [216.3], ...}`. One share point is 1.81px on the file's 5★ row, 1.97px on its 4★–2★ rows, and 2.16px in the sample chart. A 33.3% share would draw at 60px in the file's 5★ row but draws at 72px in the sample chart, about 19% longer. The same happens at 400px (tracks 184/191.8/199.7 vs 219.0). — Suggested fix: give the count and percent columns fixed widths (for example `flex: none; width: 7ch` / `5.5ch`) in both charts, or use a grid with fixed label columns, so every track has the same width. Add a check to `verify_dashboard.py` that all marks in one chart group share one track width and that `w/track` matches the saved share within 0.5%. Correct the ISSUES wording, or keep it once the scale really is shared.

MINOR — `dashboard/template.html` `renderDescribe` → `classBlock` (lines 465–481) — The "Stars' answer vs the model's answer" chart compares class totals only, so offsetting errors cancel out and the model looks almost perfect where it is not. This card is the first chart under the headline. A reader who stops there without drilling in sees near-matching bars — evidence: `measure.json` text for first100_v2: `Positive Stars 93 Model 92 · Negative Stars 7 Model 8`, while the classes section of the same run shows `Positive 91 of 93 · 2 wrong · Negative 6 of 7 · 1 wrong`. That is 3 errors hidden by a net difference of 1. The right/wrong bars do sit about one screen lower (`sec-classes` at y=1076 vs `sec-describe` at y=645), so the page as a whole passes the "without drilling in" test. — Suggested fix: print the correct count inside each Model bar (for example, split the Model bar into right and wrong segments using `per_class.X.correct`), or add one sub-line: "equal totals can hide errors that cancel; see Right answers by class".
